================================================================================
PARTE 1 - QUE ES PYDANTIC Y POR QUE EXISTE
================================================================================

Pydantic es una libreria de Python que valida y convierte datos usando las
anotaciones de tipo (type hints) que ya escribes de forma natural.

El problema que resuelve:
  En Python, un type hint como "edad: int" NO obliga a nada en tiempo de
  ejecucion. Puedes crear un objeto con edad="treinta" y Python no se queja
  hasta que algo intente usar ese valor como numero y explote mas adelante,
  lejos del origen del error. Esto es especialmente peligroso cuando los
  datos vienen de fuera: una API, un archivo JSON, un formulario, una base
  de datos. Nunca puedes confiar en que esos datos tengan la forma correcta.

Lo que hace Pydantic:
  1. Define el "contrato" de tus datos usando una clase (BaseModel) con type
     hints normales de Python.
  2. En el momento en que creas una instancia de esa clase, Pydantic REVISA
     cada campo: si el tipo no coincide intenta convertirlo de forma
     sensata (coercion), y si no puede, o si no cumple las restricciones
     (Field), lanza un error claro y detallado (ValidationError) ANTES de
     que ese dato contaminado entre al resto de tu programa.
  3. Si todo es valido, te devuelve un objeto normal de Python con todos los
     atributos ya convertidos al tipo correcto, con autocompletado y chequeo
     de tipos en tu editor.

Por que es tan usado en la industria:
  Es el nucleo de validacion de FastAPI (uno de los frameworks web mas
  usados en Python), y se usa en pipelines de datos, configuracion de apps,
  parsers de APIs externas, etc. Aprenderlo aqui no es solo un ejercicio
  academico: es una herramienta que vas a reutilizar en proyectos reales.

Pydantic v1 vs v2 (IMPORTANTE para este proyecto):
  El subject exige Pydantic 2.x. La diferencia clave que te van a preguntar:
    - En v1 se usaba el decorador @validator para validaciones personalizadas.
    - En v2 ese decorador esta deprecado; se usa @model_validator (y
      @field_validator para un solo campo). v2 tambien es mucho mas rapido
      porque su motor de validacion esta escrito en Rust (pydantic-core).
  En este proyecto usamos exclusivamente la sintaxis v2.

PARTE 2 - CONCEPTOS CLAVE QUE VAS A ENCONTRAR EN LOS 3 EJERCICIOS
================================================================================

2.1 BaseModel
--------------
Es la clase base de la que heredan todos tus modelos. Al heredar de ella,
una clase normal de Python se convierte en un "esquema validado":

    from pydantic import BaseModel

    class SpaceStation(BaseModel):
        name: str
        crew_size: int

Al escribir SpaceStation(name="ISS", crew_size=6), Pydantic valida ambos
campos automaticamente. No necesitas escribir __init__ a mano: BaseModel lo
genera por ti a partir de los type hints.

2.2 Field() y restricciones
----------------------------
Field() te deja añadir reglas extra a un campo, mas alla del tipo:

    station_id: str = Field(min_length=3, max_length=10)
    crew_size: int = Field(ge=1, le=20)
    power_level: float = Field(ge=0.0, le=100.0)
    notes: Optional[str] = Field(default=None, max_length=200)

Algunos de los argumentos mas comunes de Field:
    min_length / max_length  -> para str (y listas)
    ge / le                  -> greater-or-equal / less-or-equal (numeros)
    gt / lt                  -> greater-than / less-than (estrictos)
    default                  -> valor por defecto si no se pasa el campo

Field tambien se usa para limitar el tamaño de listas, como en ex2:
    crew: list[CrewMember] = Field(min_length=1, max_length=12)

2.3 Validacion y conversion automatica de tipos (type coercion)
------------------------------------------------------------------
Esto es EXACTAMENTE lo que te pregunta el "Think About" del ejercicio 0.

Pydantic no solo rechaza tipos incorrectos: cuando es razonable, convierte
el dato de entrada al tipo declarado. Ejemplos reales de este proyecto:
    - Un campo "last_maintenance: datetime" puede recibir el string
      "2024-01-15T08:30:00" y Pydantic lo parsea a un objeto datetime real.
    - Un campo "crew_size: int" puede recibir el string "6" y Pydantic lo
      convierte a 6 (int). Pero si recibe "seis", falla con un error claro.
    - Un campo "is_operational: bool" acepta "true", "1", "yes", etc.

Esto es util cuando los datos vienen de JSON/CSV (todo llega como string),
pero OJO: en el codigo de este proyecto, los main() escriben los valores
como objetos Python ya tipados (ej. datetime(2024, 1, 15, 8, 30) en vez de
un string) para que herramientas de tipado estatico como mypy no se quejen.
La conversion automatica SI sigue funcionando igual si tu le pasas un string
a mano (pruebalo en el REPL, ver Parte 4.4).

2.4 ValidationError
----------------------
Cuando un modelo no cumple las reglas, Pydantic no devuelve None ni un
booleano: lanza una excepcion ValidationError con el detalle exacto de que
campo fallo y por que. En este proyecto siempre se captura asi:

    from pydantic import ValidationError

    try:
        SpaceStation(crew_size=25, ...)
    except ValidationError as error:
        print(error.errors()[0]["msg"])

error.errors() devuelve una LISTA de diccionarios (puede haber varios campos
invalidos a la vez), cada uno con claves como:
    "loc"   -> en que campo ocurrio el error, ej. ("crew_size",)
    "msg"   -> mensaje legible, ej. "Input should be less than or equal to 20"
    "type"  -> tipo de error, ej. "less_than_equal"
    "input" -> el valor que se intento usar

Tip de estudio: en tu REPL, imprime "error.errors()" completo (no solo
el primer item) para ver toda la info que te da Pydantic. Tambien existe
"str(error)" que da un resumen en texto formateado de todos los errores.

2.5 Enum
-----------
Un Enum limita un campo a un conjunto cerrado de valores validos. En este
proyecto heredamos de (str, Enum) para que el valor tambien se comporte
como string (facil de imprimir, comparar, exportar a JSON):

    class ContactType(str, Enum):
        RADIO = "radio"
        VISUAL = "visual"
        PHYSICAL = "physical"
        TELEPATHIC = "telepathic"

Si le pasas contact_type="laser" (no es un valor del enum), Pydantic lanza
ValidationError automaticamente. No necesitas validarlo tu mismo.

2.6 model_validator(mode="after")
-------------------------------------
Field() valida UN campo de forma aislada (ej: "crew_size entre 1 y 20").
Pero algunas reglas de negocio dependen de VARIOS campos a la vez, o de
relaciones entre ellos. Para eso existe @model_validator.

    @model_validator(mode="after")
    def check_business_rules(self) -> "AlienContact":
        if not self.contact_id.startswith("AC"):
            raise ValueError('Contact ID must start with "AC"')
        ...
        return self

Puntos clave:
    - mode="after" significa que este metodo corre DESPUES de que todos los
      campos individuales ya pasaron su propia validacion (Field, tipos,
      enum, etc). Es decir: cuando entras a esta funcion, self.crew_size ya
      es un int valido entre 1 y 20, self.contact_type ya es un ContactType
      valido, etc. Tu solo te preocupas de la logica de negocio.
    - Dentro del validador simplemente lanzas "raise ValueError(mensaje)" si
      algo no cumple la regla. Pydantic automaticamente convierte ese
      ValueError en una ValidationError con tu mensaje adentro.
    - SIEMPRE debes "return self" al final si todo esta bien. Si se te
      olvida, Pydantic entiende que el modelo "after" quedo en None y falla.
    - mode="after" te da acceso a "self" ya como instancia del modelo (osea
      self.contact_type ya es el Enum, no un string). Existe tambien
      mode="before" que corre ANTES de la validacion de campos individuales,
      y recibe datos crudos (dict), pero NO se usa en este proyecto.

2.7 Modelos anidados (nested models) - solo en ex2
-------------------------------------------------------
Un campo de un modelo puede ser directamente OTRO modelo Pydantic, o una
lista de otro modelo:

    class SpaceMission(BaseModel):
        ...
        crew: list[CrewMember] = Field(min_length=1, max_length=12)

Cuando creas un SpaceMission, Pydantic valida CADA CrewMember de la lista
individualmente (sus propios Field, su propio Rank enum, etc) ANTES de
pasar al model_validator de SpaceMission. Si un solo CrewMember de la lista
es invalido (ej: age=200), la creacion de todo el SpaceMission falla con un
ValidationError que indica en que posicion de la lista y en que campo
ocurrio el problema (ej: loc = ("crew", 2, "age")).

Esto es justo lo que pregunta el "Think About" del ejercicio 2.

2.8 Optional y valores por defecto
--------------------------------------
    notes: Optional[str] = Field(default=None, max_length=200)
    is_operational: bool = True
    mission_status: str = "planned"

Optional[str] es equivalente a "str | None": el campo puede ser un string
O puede faltar/ser None. Si un campo tiene un "default", no es obligatorio
pasarlo al crear el modelo.

PARTE 5 - EJERCICIO 1: ALIEN CONTACT LOGS (ex1/alien_contact.py)
================================================================================

5.1 Que aprendes aqui
------------------------
Se añaden dos conceptos nuevos sobre lo de ex0:
    - Enum (ContactType): el campo contact_type solo acepta "radio",
      "visual", "physical" o "telepathic".
    - @model_validator(mode="after"): reglas de negocio que dependen de
      la COMBINACION de varios campos, no de un campo aislado.

5.2 Recorrido del codigo
----------------------------
class ContactType(str, Enum):
    RADIO, VISUAL, PHYSICAL, TELEPATHIC

class AlienContact(BaseModel):
    contact_id: str                (5-15 caracteres)
    timestamp: datetime
    location: str                   (3-100 caracteres)
    contact_type: ContactType
    signal_strength: float          (0.0-10.0)
    duration_minutes: int           (1-1440, max 24h)
    witness_count: int              (1-100)
    message_received: Optional[str] (hasta 500 caracteres)
    is_verified: bool = False

    @model_validator(mode="after")
    def check_business_rules(self):
        1) contact_id debe empezar con "AC"
        2) si contact_type == PHYSICAL  -> is_verified debe ser True
        3) si contact_type == TELEPATHIC -> witness_count >= 3
        4) si signal_strength > 7.0      -> message_received no puede faltar

Fijate que las 4 reglas se evaluan EN ORDEN, y la validacion se detiene en
la PRIMERA que falle (porque usamos "raise" directo, no acumulamos errores
como hace Field automaticamente). Esto es una decision de diseño: para
reglas de negocio simples como estas, basta con el primer error encontrado.

En main():
    - Caso valido: un contacto RADIO con señal 8.5 (>7.0) que SI trae
      mensaje, cumpliendo la regla 4.
    - Caso invalido: un contacto TELEPATHIC con solo 1 testigo (viola la
      regla 3), capturado con try/except ValidationError.

5.3 Como probarlo paso a paso
---------------------------------
1) Con el venv activado, desde la raiz de Module_09:

     python ex1/alien_contact.py

   Salida esperada:

     Alien Contact Log Validation
     ======================================
     Valid contact report:
     ID: AC_2024_001
     Type: radio
     Location: Area 51, Nevada
     Signal: 8.5/10
     Duration: 45 minutes
     Witnesses: 5

   model_validator (para diferenciarlos de los errores automaticos de
   Field, que no llevan ese prefijo).

      nunca llega a ejecutar el model_validator si un campo ya fallo antes.

PARTE 6 - EJERCICIO 2: SPACE CREW MANAGEMENT (ex2/space_crew.py)
================================================================================

6.1 Que aprendes aqui
------------------------
El concepto nuevo principal es el MODELO ANIDADO: SpaceMission contiene una
lista de objetos CrewMember, y cada CrewMember es a su vez un BaseModel
completo con sus propias reglas. Tambien se combina con Enum (Rank) y
model_validator (mode="after") con reglas que dependen de TODA la lista.

6.2 Recorrido del codigo
----------------------------
class Rank(str, Enum):
    CADET, OFFICER, LIEUTENANT, CAPTAIN, COMMANDER

class CrewMember(BaseModel):
    member_id: str              (3-10 caracteres)
    name: str                    (2-50 caracteres)
    rank: Rank
    age: int                      (18-80)
    specialization: str          (3-30 caracteres)
    years_experience: int         (0-50)
    is_active: bool = True

class SpaceMission(BaseModel):
    mission_id: str               (5-15 caracteres)
    mission_name: str             (3-100 caracteres)
    destination: str              (3-50 caracteres)
    launch_date: datetime
    duration_days: int             (1-3650, max 10 años)
    crew: list[CrewMember]          (1-12 miembros)
    mission_status: str = "planned"
    budget_millions: float          (1.0-10000.0)

    @model_validator(mode="after")
    def check_safety_rules(self):
        1) mission_id debe empezar con "M"
        2) debe haber al menos un COMMANDER o CAPTAIN en self.crew
        3) si duration_days > 365 -> al menos 50% de la tripulacion debe
           tener years_experience >= 5
        4) todos los miembros de self.crew deben tener is_active == True

Lo importante: cuando llamas SpaceMission(crew=[CrewMember(...), ...]),
Pydantic primero valida CADA CrewMember de la lista de forma individual
(sus Field, su Rank enum). Solo si TODOS los CrewMember son validos,
Pydantic continua y arma la lista "self.crew", y DESPUES corre el
check_safety_rules de SpaceMission, donde ya puedes recorrer self.crew
tranquilamente porque sabes que cada item ya es un CrewMember 100% valido.

En main():
    - Caso valido: mision a Marte con 3 miembros, incluyendo una Commander.
    - Caso invalido: mision a Venus con un solo Cadet (viola la regla 2:
      no hay Commander/Captain).

6.4 Experimentos sugeridos
-------------------------------
   a) Probar que un CrewMember invalido DENTRO de la lista rompe toda la
      mision, y ver donde reporta Pydantic el error exacto (posicion en
      la lista + campo).

      IMPORTANTE: para que Pydantic te reporte la posicion dentro de la
      lista (ej. "el elemento 1 de crew"), tienes que pasarle DICCIONARIOS
      en vez de objetos CrewMember ya construidos. Si escribes
      CrewMember(age=150, ...) directamente dentro de la lista, Python
      construye ese CrewMember ANTES de llamar a SpaceMission, y el
      ValidationError salta ahi mismo (con loc=('age',), sin mencionar
      "crew"), porque SpaceMission ni siquiera llega a recibir el dato.
      Pasando dicts, en cambio, es Pydantic quien construye cada
      CrewMember DENTRO del proceso de validacion de SpaceMission, y por
      eso puede reportar la ruta completa:

        from ex2.space_crew import SpaceMission, Rank
        from datetime import datetime
        from pydantic import ValidationError

        try:
            SpaceMission(
                mission_id="M9999999", mission_name="Test Mission",
                destination="Moon", launch_date=datetime.now(),
                duration_days=10, budget_millions=5.0,
                crew=[
                    {"member_id": "CM1", "name": "Ok Person",
                     "rank": Rank.COMMANDER, "age": 40,
                     "specialization": "Command", "years_experience": 10},
                    {"member_id": "CM2", "name": "Bad Age",
                     "rank": Rank.OFFICER, "age": 150,   # invalido!
                     "specialization": "Science", "years_experience": 2},
                ],
            )
        except ValidationError as e:
            for err in e.errors():
                print(err["loc"], "->", err["msg"])

      Esto imprime exactamente:
        ('crew', 1, 'age') -> Input should be less than or equal to 80

      O sea: el elemento en indice 1 (el segundo) de la lista "crew" tiene
      un problema en su campo "age". Esta es una leccion clave sobre como

      reportar la ruta completa del error. Si tu construyes el sub-modelo

la demostracion de la conversion automatica (que puedes seguir probando a

Que es el .tar y para que sirve
-------------------------------
El subject (seccion III.3 "Available Tools") entrega data_generator.tar con:

  * data_generator.py  -> genera datos "realistas" (estaciones, contactos
                          alienigenas, misiones con tripulacion).

                          y .py dentro de generated_data/.

NO es parte de la entrega: ningun ejercicio exige usarlo, y el main() de
cada ejercicio debe seguir imprimiendo exactamente la salida del subject.
Sirve solo para PROBAR tus modelos con muchos datos (validos e invalidos),
justo lo que harias en la vida real: datos que vienen de afuera (un JSON)
pasan por tu modelo Pydantic antes de usarse.

Como quedo organizado
---------------------
  Module_09/
    tools/                    <- contenido extraido del .tar
      data_generator.py
      data_exporter.py
      generated_data/         <- JSON/CSV/.py generados
        space_stations.json     (10 estaciones validas)
        alien_contacts.json     (15 contactos validos)
        space_missions.json     (5 misiones validas)
        invalid_stations.json   (2 estaciones invalidas a proposito)
        invalid_contacts.json   (2 contactos invalidos a proposito)
      test_with_data.py       <- script que prueba ex0/ex1/ex2 con esos JSON

tools/ y el .tar estan en .gitignore: el codigo del subject no cumple
flake8/mypy (ej: le faltan anotaciones de tipo), y si lo subes al repo,
"flake8 ." y "mypy ." en la evaluacion fallarian por codigo que no es tuyo.

Como usarlo
-----------
Con el venv activado, desde la raiz de Module_09:

  1) (Re)generar los datos (la semilla es fija, siempre salen los mismos):
       cd tools && python data_exporter.py && cd ..

  2) Probar los tres modelos contra los datos:
       python tools/test_with_data.py

Resultado esperado: todos los registros de space_stations.json,
alien_contacts.json y space_missions.json salen "OK", y los de los
archivos invalid_*.json salen "ERROR" con el motivo, por ejemplo:

  ERROR TOOLONG123456: String should have at most 10 characters
  ERROR WRONG_FORMAT: Value error, Contact ID must start with "AC"
  ERROR AC_2024_002: Value error, Telepathic contact requires at least 3
        witnesses

Fijate en dos cosas que te sirven para la defensa:
  * Los JSON traen las fechas como STRING ISO ("2024-01-15T10:30:00") y
    Pydantic las convierte solas a datetime (Parte 2.3). Tambien
    contact_type llega como "radio" y se convierte al Enum ContactType.
  * space_missions.json trae la tripulacion como lista de dicts, y
    SpaceMission(**datos) construye los CrewMember anidados solo.
    Por eso el modelo se crea con model(**record): se "desempaqueta" el
    dict en argumentos con nombre.

Experimento extra: edita a mano un registro de generated_data/*.json
